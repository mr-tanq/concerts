# Ticket Intelligence V2

## Repository audit

Baseline: `main` at `439bddff0bcc878817288a8b8caed23a9db11d01`. Listening Mirror is a static, mobile-first GitHub Pages PWA. The Live tab reads the recommendation deck and Going plan from repository JSON. TicketSwap is already mounted in Going cards and their concert sheets. The card creates a GitHub Contents API request in `data/ticketswap-requests.json` after a user action. An Actions worker checks the planned concert identity and writes `data/ticketswap.json`. The browser tracks the matching request ID through GitHub so it can display a result before Pages catches up.

Reuse `planned.json` for owned-ticket state and concert identity, the existing event matcher, the card's disclosure and text styles, the Contents API's SHA conflict handling, and the existing Pages snapshot. Discovery already has Last.fm affinity, a scored recommendation deck, location configuration, official festival sources, and venue and organizer links. The existing search adapters carry `ticketUrl`, `sourceUrl`, and sometimes `officialUrl`; several links lead to aggregators and need source verification. The audit found no dedicated Ticketmaster price adapter. Treat Ticketmaster as a future source when linked or otherwise available through an authorized integration.

The Supabase migration serves the Android media and now-playing relay through private data and RPCs. Keep that boundary intact for V2.1. New private ticket storage could eventually use a dedicated schema and scoped access after reviewing relay credentials and testing ownership controls. Paperworld's repository metadata and trusted test gate already establish a project boundary. Luna should read a Listening Mirror-owned projection in a later phase.

Current main has the repaired POST adapter and strict automatic matching with a human review path. PR #9 proposes a one-minute browser TTL and basic candidate filtering. Its refresh timestamp starts before the request completes, its promise can overwrite a newer result, the early-return on populated panels still prevents reopening from revalidating, and the duplicated matching heuristic omits venue and country conflicts. V2.1 incorporates the TTL and review filter through shared code, an in-flight promise that is independent of freshness, and a timestamp guard. PR #39 was closed after an external scraper repair. Preserve the active adapter.

Other risks include first-page bias, incomplete category coverage, a main-branch runtime that depends on successful GitHub writes, concurrent request commits, the discontinuity between observed credit balance and ledger initialization, and an offline service-worker fallback that can return an old successful snapshot. Use observation age in the UI even when transport succeeds. The current Actions concurrency group allows one running and one pending run and can replace pending runs. Refresh workers read current main at startup to pick up coalesced writes. The existing processing limit is three concerts per run. Unprocessed requests may require another manual trigger. Resolve durable queue draining before introducing scheduled monitoring.

## V2.1 behavior

- Keep existing user-triggered checks. A GET of the static snapshot is free. There is no new polling schedule. The existing browser only polls GitHub for the result of a manual check.
- Revalidate a reopened panel after 60 seconds. Concurrent cards share one snapshot fetch. Keep usable prior data on failure, surface the saved observation time, and reject older snapshots when a newer GitHub result has arrived. The service worker can serve an offline copy, whose observation time still applies.
- Resolve events using local date, artist billing, venue, city, country, and safe TicketSwap URLs. A user can confirm ambiguous artist billing when date, city and venue agree and the country is compatible. Never submit a selection to the provider directly from the browser. The worker repeats the policy against previously stored candidates and the current concert identity. Legacy confirmations without location evidence are re-resolved on the next paid check. Legacy automatic matches remain reusable for unchanged identity.
- Search can surface weak matches for diagnostics. Missing pagination metadata means completeness is unknown. A unique strong match in the returned page still follows the existing automatic selection policy. Event ID validation on the listings response and each listing guards against cross-event attribution.
- A complete empty page shows zero. An incomplete empty page shows zero in the checked listings. A missing or invalid response shows an unknown state or the last usable observation with a failure message. Deduplicate listings by ID before computing quantity. Omit invalid or non-EUR totals. The minimum with incomplete coverage or invalid prices is the lowest observed valid price.
- Successful availability advances `checkedAt`. Each attempt advances `lastAttemptAt`; failed attempts keep the last successful availability, price, coverage and timestamp for the same concert identity. A candidate that conflicts with a previously observed event must complete successfully before replacing its event association.
- Keep the existing version 1 snapshot readable. V2.1 stores only the existing compact summary, safe matching metadata and safe diagnostics. Raw listing bodies and seller data stay out of snapshots and logs.

## Data models

| Record | Fields and invariants |
| --- | --- |
| Concert match | Internal concert ID, identity tuple (artist/date/venue/city/country), source event ID, safe URL, title, location evidence, automatic/user-confirmed provenance. Re-resolve on changed identity. |
| Snapshot v1 | Version, publication time; entries keyed by concert ID with identity, event, status, request ID, last attempt, last success, last error, count, lowest buyer total in EUR cents and coverage. Search result status is distinct from market availability. |
| Listing observation | Provider event and type IDs, listing ID, verified URL, status, remaining quantity and lot size; original, seller and final buyer money, observed time and coverage. Dedupe within a sample. Avoid seller profile data. |
| Money | Integer minor amount, ISO currency, source field and conversion provenance. Unknown is null. Validate currency and units before conversion or comparison. Record service fees only as verified fields or the difference between comparable known seller and buyer totals on the same basis. |
| Category | Provider type ID, event ID, title, entrance/other/unknown, organizer display price, and explicit official category mapping when supported by evidence. Attendance, days, seating and access terms are part of equivalence. A missing type is unknown. |
| Market observation | Event/type, observation time, fetch status and sample boundaries; buyer floor, price range and median, SOLD sample median, quantities, face-value evidence, official offer reference and demand signals. Record sample size, coverage per group, currency and basis. A SOLD listing contributes at observation time only as part of a sample, never as a dated trade. |
| Official offer | Event, category, seller, official purchase and source URL, face amount, current base, fees and final amount, currency, availability state, evidence and verification time. Keep separate from both TicketSwap original and organizer price. Unknown fields stay null. |
| Watch | Authenticated owner, internal concert ID, quantity, category preference, maximum final buyer amount, alert types, state, next eligible check, and suspension reason. Past events and owned tickets are ineligible. |
| Alert | Watch ID, condition, qualifying offer fingerprint, eligibility transition, evidence, created time and delivery state. Persist dedupe keys and process via idempotent outbox. |
| Credit ledger v1 | UTC date to accounted usage, per-endpoint estimated/verified/accounted totals and count of unverified requests, nullable remaining budget before initialization, and backoff deadline. No API credentials or response bodies. |
| Opportunity | Event and category, evidence references, freshness, provenance, affinity, eligibility, scoring reasons, and optional savings. Computed from existing records. |

## Credit policy and operations

The supplied 194 is an initial configurable balance estimate. It has no assumed renewal. Before first approved operation reconcile it against the account display. Set repository variables `TICKETSWAP_INITIAL_CREDITS` (default 194), `TICKETSWAP_DAILY_LIMIT` (8), `TICKETSWAP_MONTHLY_LIMIT` (40), and `TICKETSWAP_CREDIT_RESERVE` (20). Zero daily or monthly limit suspends new requests. UTC caps and the rolling ledger balance must all permit the next debit. The monthly cap controls spending within a calendar month; changing months does not add balance. After initialization, changing the initial variable leaves the persisted balance intact. On a known top-up or outside debit, reconcile the ledger explicitly while both workflows are idle. Never initiate a top-up.

The live refresh and diagnostic use the same Actions concurrency group and latest main checkout. Before HTTP, the worker commits the estimated debit to the ledger on main. A failed write prevents the call. An interrupted run retains the debit at its estimate. A successful push is required for each charge; branch protection or a competing write can pause work. Current balance and daily usage are estimates wherever provider charges are unavailable. Verified charges reconcile the difference. Enable `TICKETSWAP_TRUST_CREDIT_HEADERS=true` only after verifying `X-Credits-Charged` and `X-Credits-Remaining` against the account. Remaining headers can lower the local balance. The ledger exposes aggregate operational counts in the existing GitHub data store. Supabase or a separate service is unnecessary for this phase.

Deduplicate identical endpoint/parameter requests, reuse successful responses for five minutes within a worker, and serialize distinct calls. Across workers reuse the shared availability snapshot and remembered event ID, with the existing per-concert manual cooldown and six-hour bulk refresh eligibility. Raw provider response caching across runs is deferred. A failed request has zero automatic retries, consumes its estimated debit absent verified reporting, and pauses further requests for at least one minute or the supported numeric `Retry-After` value up to an hour. HTTP 402 suspends the remaining budget. An outage, unknown price or partial response cannot trigger a paid retry loop. The diagnostic smoke workflow is manual and consumes the same budget.

For scheduled monitoring in a later phase, reuse resolved type IDs, try AVAILABLE_ONLY batches of up to ten, and reserve FULL_MARKET batches of up to five for high-interest or stale deep samples. Use sold samples to recover IDs where availability is empty. Keep the scheduler disabled until explicitly approved.

### V2.2 availability and history increment

The existing budgeted `get_event_listings` check supplies the first market view without any additional provider calls. Snapshot v1 has two optional fields. `market` holds the number of active listings, EUR buyer floor/range/median (one price per unique active listing), grouped ticket types, and the lowest observed offer. Category rows use exact provider type IDs and an explicit unknown category when absent. A listing link requires a safe TicketSwap listing path. Stored links omit search and fragment values. This increment uses the same EUR integer Money representation as the existing buyer-total adapter; malformed or ambiguous components remain unknown. The buyer–seller difference uses two amounts from the same currency bundle and is labeled as a difference. An independently verified fee schedule requires its own evidence.

`marketHistory` holds the last 24 successful observations for the same concert identity and TicketSwap event. The prior saved availability snapshot can contribute its actual check timestamp and existing values. Unknown prices and zero-availability checks have no price bar. Partial checks are labeled as samples. Failed refreshes retain the last useful details without creating an observation. Older published snapshots continue to use the basic panel. The browser shows a price-drop observation only when both recent checks have explicit complete coverage and valid prices throughout. Individual categories or the set of listings can change between observations.

SOLD sampling, demand and type-market aggregates still await verified endpoint contracts and approval. This increment leaves those sources dormant and makes no completed-sale, demand, overall market coverage, or official availability claims.

### V2.3 official offer evidence

Official availability and price use a separate versioned snapshot, `data/official-ticket-offers.json`, keyed by planned concert identity. The comparison panel also recognizes existing official venue/organizer links and direct Ticketmaster event links. Aggregator links retain their existing UI and do not supply official prices. Official offers currently enter through a reviewable local import, rather than an automated checkout scraper. The import performs no network requests and makes no purchase.

After checking the official seller's current checkout for one ticket, run `node scripts/record-official-offer.mjs path/to/offer.json` from the repository root and review the JSON diff. Input keys are `concertId`, `seller`, `category`, `sourceUrl`, `purchaseUrl`, `verifiedAt` (ISO timestamp), `evidence` (short source note without customer or checkout session data), `quantity` (1), `availability` (`available`, `sold-out`, or `unknown`), `currency` (ISO code), and optional integer minor amounts `faceCents`, `baseCents`, `feesCents`, `finalCents`. Supply `feeInclusive: true` only with a verified all-in final amount, and leave unknown amounts null. An optional `resaleTypeId` requires `equivalenceEvidence` documenting matching event date, access, seating and ticket terms. The importer validates the ID against the same concert's TicketSwap snapshot, and stores the exact TicketSwap event ID. Use public event or offer URLs without cart tokens or personal data.

The browser compares only fresh, same-currency, available offers, with a maximum age of six hours for both sides. TicketSwap must show an explicitly single-ticket listing for the mapped category. Missing lot-size fields and older snapshots without a single-ticket buyer total cannot produce a savings figure. The label identifies sampled data or a single-ticket subset where relevant. Absolute savings and the percentage use the official final total as the reference. The UI displays the verified source, timestamp, and separate purchase links. TicketSwap-reported face value remains separate. The checked-in offer store starts empty because no official checkout evidence has been supplied.

### V2.3.1 official ticket providers

The on-demand collector checks one upcoming planned concert. It reuses direct official URLs and the official event pages already saved by concert schedule discovery. Dutch venue and organizer hosts are scoped by the existing publisher registry. Direct Dutch and Belgian Ticketmaster event URLs have a separate primary-ticket policy. A venue offer can link to a known Stager purchase page already recorded for the concert. Podiuminfo and Festivalinfo links remain discovery evidence and do not establish price or stock. No Cloudflare Worker sources, Wrangler configuration, or dedicated Ticketmaster feed were found in this repository. The collector has no Worker or paid API dependency.

Run `node scripts/refresh-official-tickets.mjs CONCERT_ID` for an offline source preview. Pass `--live` for a one-shot public check and local snapshot update. The GitHub workflow **Refresh official ticket offers** provides the same explicit dispatch, defaults to a preview and has no schedule or push trigger. The ordinary TicketSwap check does not trigger any official-page requests.

The structured-data provider matches one Event or MusicEvent by date, venue, city and billing, checks a supplied country and skips ambiguous matches. It reads named offers and explicit stock states. Aggregate prices, undated checkout evidence and ambiguous availability are not promoted to current offers. A plain structured price is displayed as a published price. Separate base and fees require explicit component labels. An all-in amount additionally requires an explicit inclusive total and single-ticket quantity, consistent currency and consistent known components. Ticketmaster collection only accepts explicitly named primary standard ticket offers. Unsupported pages keep official price or availability unknown. Use the manual import for unsupported checkout providers and fee evidence.

The optional `data/official-ticket-category-mappings.json` is an array of reviewed mappings. Each mapping supplies `concertId`, `identity` (the snapshot identity), `sourceUrl` (the canonical evidence URL), `offerKey` (the structured offer SKU), `category` (the exact official label), `resaleEventId`, `resaleTypeId`, and `equivalenceEvidence`. The collector automatically reapplies an exact mapping only when there is a unique matching official SKU and a category under the current matching TicketSwap event. An absent or stale mapping still allows displaying evidence and does not allow a savings comparison.

The collector obeys the publisher's robots policy and declines checks when it cannot verify permission. It allows only HTTPS requests to an approved publisher, with bounded same-publisher redirects, response size and timeout, and no authentication or repeated attempts. Identical in-process requests share one fetch. Persisted results last one hour, and temporary failures suppress new requests for 15 minutes. Publisher access and rate-limit responses pause the host for at least an hour and honor a longer `Retry-After`. Failed refreshes keep prior evidence with its original timestamp and suppress a current comparison. Automated evidence is stored separately from manual records and contains no raw HTML. The browser retains the existing six-hour freshness policy.

### V2.4 Smart Ticket Watch

The Going view has a Watchlist, and each Going concert can be watched from its TicketSwap panel. Watching requires the existing connected GitHub repository. Preferences are stored in `data/ticket-watches.json` and observations, scheduler estimates, lifecycle status and up to 12 recent notifications per watch are stored in `data/ticket-watch-state.json`. These files have the same visibility as the repository. The Watchlist shows timestamps, saved observations and in-app alert history. It never purchases tickets or credits. A paused, past, owned or removed concert cannot enter a monitoring pass. A verified schedule end can stop same-day checks. Re-adding a removed watch starts a new watch and alert history.

A qualifying listing must explicitly supply the desired exact lot quantity, with an EUR final buyer amount where pricing is required. The limit is per ticket. Listings with unknown lot size and incomplete pages cannot prove absence. For confirmed availability, threshold and last-minute alerts, a positive observation can suffice even when results are partial. Price-drop alerts compare observations with complete relevant price coverage. Signals re-arm on definite transitions and are deduplicated by watch, event and observation. Last-minute means within two calendar days of the concert date. Observations can age out and failed checks retain the prior successful data. By default manual TicketSwap checks also evaluate matching watches from the saved snapshot with no extra provider traffic. Notifications are shown in the app.

The scheduler preview reports the estimated next pass, due watch count and protected credit reserve. The live scheduler and manual TicketSwap workflow share the serialized credit worker and durable ledger. The planner reuses event and category IDs, uses availability batches of up to ten types, and falls back to existing event listings for all-category or unresolved watches. Cadence adapts to concert proximity, preference specificity and spendable credits. Optional FULL_MARKET batches use at most five types. An explicit enrichment run can spend at most two additional credits on event SOLD sampling and demand after core work. SOLD listings are sampled observations, and demand text is preserved without inferred counts. Evidence is never treated as a verified transaction.

There is no scheduled trigger. The Smart Ticket Watch workflow defaults to a no-provider preview. A live dispatch also requires both repository flags `TICKETSWAP_WATCH_ENABLED` and `TICKETSWAP_WATCH_CONTRACTS_VERIFIED`. Repository budgets, remaining balance and reserve still apply. Preview from the checkout with `node scripts/run-ticket-watches.mjs`. Review the estimate before authorization. The new adapters use the documented GET transport with JSON query encoding for arrays; existing endpoints retain POST. New endpoint method, array encoding, envelopes, page shape, identity fields, exact lot counts, EUR price semantics and credit headers still need explicitly approved live validation. Until that validation succeeds, leave the contract and live flags unset.
